# NInfer 입력 깊이별 성능 및 Codex 검증 — 2026-09-09

[English](ninfer-qualification-2026-09-09.md) · [한국어](ninfer-qualification-2026-09-09.ko.md) · [벤치마크 목록](README.ko.md)

**결정: Q5/MTP3를 기본값으로 유지하고, NInfer는 검증 후보로 둡니다.** NInfer는 디코딩·회상 검사를 통과했습니다. 최초 Codex 도구 왕복 호출은 Responses 호환성 오류로 실패했고, 어댑터의 제한적인 수정 후 같은 94K 작업을 통과했습니다. 전체 자율 작업 검증은 아닙니다. Q5는 다시 측정하지 않았습니다.

## 측정된 디코딩 속도와 기존 Q5 비교

[통합 보고서(영문)](ninfer-integration-2026-09-08.md)와 동일하게 고정된 NInfer 모델 파일·드라이버·런타임을 사용했습니다. FP8 KV, MTP3, thinking 끔, 240K 할당, 동시 요청 1입니다. 각 입력 깊이에서 워밍업 1회 후 3회 측정했으며, temperature 0, 출력 300토큰입니다. 아래 값은 **서버 로그의 디코딩 속도**로, 출력 토큰 수를 요청 전체 경과 시간으로 나눈 값이 아닙니다.

| 기존 깊이 표기 | 기존 Q5 중앙값 tok/s | NInfer 중앙값 tok/s | NInfer 최솟값–최댓값 | NInfer 실제 프롬프트 토큰 | 제안 토큰 수락률 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 짧은 입력 | 151.72 | 222.0 | 222.0–222.5 | 54 | 83.92% |
| 32K | 120.29 | 190.6 | 190.6–190.6 | 38,717 | 75.55% |
| 80K | 98.59 | 176.9 | 176.8–176.9 | 83,917 | 73.84% |
| 114K | 94.66 | 169.8 | 169.7–169.9 | 113,956 | 75.82% |

기존 Q5 입력 생성기는 32K/80K/114K라는 표기와 달리 지시문·템플릿 추가 전 38,673 / 83,873 / 113,912토큰을 생성했습니다. NInfer는 동일 생성기의 근거 단위 5/11/15개와 같은 RepositoryIndex 생성 지시문을 재사용했습니다. 짧은 프롬프트는 NInfer 54토큰, 기존 Q5 약 725토큰으로 다르므로, 그 비율을 동일 프롬프트의 속도 향상률로 볼 수 없습니다. 모델 파일, 채팅 템플릿, API, 캐시 구현도 달라 차이를 런타임에만 귀속할 수 없습니다.

긴 입력에서 디코딩 속도는 기존 Q5 값의 약 1.58 / 1.79 / 1.79배였습니다. **과거 결과와의 비교이며 같은 시점의 A/B 실험이 아닙니다.** 측정 12회에서 3,600토큰을 생성했고, 제안 토큰 3,243개 중 2,502개를 수락했습니다(77.15%). 디코딩은 빨랐지만 제안된 목표 85–90%에는 못 미쳤습니다. 기존 Q5의 89.61%는 에이전트 작업에서 측정한 값으로, 동일 조건의 수락률 기준값이 아닙니다.

실행별 토큰 수·프롬프트 해시·시간·제안 토큰 수: [JSON](ninfer-depth-2026-09-09.json). 재현 도구: [compare-runtimes.py](../scripts/compare-runtimes.py).

## 프리필, 캐시, 메모리

TTFT는 클라이언트에서 측정한 첫 토큰 도착까지의 시간입니다.

| 입력 깊이 | 워밍업 TTFT | 반복 프롬프트 TTFT 중앙값 | 반복 프롬프트 전체 경과 시간 중앙값 |
| --- | ---: | ---: | ---: |
| 38K | 5.537 s | 0.072 s | 1.645 s |
| 84K | 16.205 s | 0.087 s | 1.783 s |
| 114K | 25.959 s | 0.097 s | 1.864 s |

반복 프롬프트에서는 거의 모든 입력 토큰을 재사용했습니다. 이 짧은 TTFT를 캐시 없는 긴 입력의 프리필 성능으로 제시하면 안 됩니다. 별도의 캐시 없는 회상 요청에서 38K / 84K 프리필은 약 7.06K / 5.21K tok/s였고, 세 깊이의 클라이언트 TTFT는 5.514 / 16.148 / 25.861초였습니다.

GPUQ가 관측한 실행 중 장치 전체 최대 메모리 사용량은 29,436 MiB입니다. 다른 장치 할당도 포함하므로 프로세스 전용 할당량이나 연속 표본으로 구한 최소 여유 메모리가 아닙니다. 런타임은 여전히 호스트 상태/KV 캐시를 사용합니다. 보존된 서버 로그에서는 CUDA/OOM 오류가 관측되지 않았습니다. **160K–240K 작업은 실행하지 않았습니다.**

## 정확성과 실패

| 검증 항목 | 관측 결과 |
| --- | --- |
| 기본 지시 이행 | 3/3 |
| 강제 JSON 스키마 | 미지원: HTTP 400 `response_format_not_supported` |
| 최초 일반 JSON 프롬프트 | 엄격한 파싱 0/20; 응답에 Markdown 코드 펜스 포함 |
| JSON 원문만 출력하도록 명시한 별도 진단 | 20/20; 별도 프롬프트 변형이며 스키마 강제 없음 |
| 단일 턴 도구 이름·인자 | `read_file` 요청 40/40 |
| 38K / 84K / 114K 회상 | 각 깊이에서 사실 5/5; 스키마에 정답 없음 |
| 제약된 Python 코딩 픽스처 | 작업 2/3; 각 작업은 워밍업 후 3회 반복 |
| 실제 Codex 읽기·수정·테스트 왕복 | 최초 FAIL; 수정 후 제한된 재검증 PASS (테스트 3/3) |

Python `unique` 함수는 `list.append`를 사용해 속성 접근을 금지한 의도적인 픽스처 제약을 위반했습니다. 코드가 깨진 것은 아닙니다. 나머지 두 함수는 테스트 벡터를 통과했습니다. JSON 전용 지시의 성공이 최초 파싱 실패를 없애거나 강제 생성 지원을 뜻하지는 않습니다. [별도 JSON 진단](../scripts/probe-json-explicit.py)을 참고하세요.

기존 Q5 NIAH는 정답이 포함된 enum 스키마를 사용했으므로, 정답을 제공하지 않은 NInfer 회상 검사와 동등하지 않습니다. NInfer 검사는 입력의 10/25/50/75/90% 위치에 있는 사실 5개를 물었습니다. 회상 성공만으로 해당 깊이의 코딩 성능을 입증할 수는 없습니다.

## 94K에서 발생한 실제 Codex 실패

Codex CLI 0.153.4에 84K 참조 컨텍스트와 일반 지시문·도구를 제공했고, 실제 프롬프트는 94,338토큰이었습니다. 격리된 작업은 작은 JavaScript 합계 함수를 읽고 짝수 정수만 합산하도록 수정하되 테스트를 유지하고 `node sum.test.cjs`를 실행하는 것이었습니다.

첫 도구 요청은 소스와 테스트를 정상적으로 읽었습니다. 다음 왕복에서 어댑터/업스트림이 아래 오류를 반환했습니다.

```text
parameter_not_supported
unsupported input member: internal_chat_message_metadata_passthrough
```

31.253초 후 종료 코드 1로 끝났습니다. 의미 있는 수정은 0건이었고, 독립적으로 다시 실행한 테스트도 실패했습니다(`10 !== 6`). 성공한 생성 1회의 로그는 188.2 tok/s, 제안 토큰 39개 중 35개 수락이지만 출력이 46토큰뿐이므로 **대표적인 에이전트 평균 TPS로 주장하지 않습니다.** 기존 CourseBench의 109.51 tok/s를 능가하거나 대체하는 결과가 아닙니다.

이는 긴 컨텍스트의 제한된 에이전트 검사이며 전체 CourseBench 재실행이 아닙니다. 최초 측정 시도에는 런타임이나 어댑터 수정을 반영하지 않았습니다.

## 수정 후 Codex 재검증

NInfer 전용 어댑터는 Responses 입력 항목의 `internal_chat_message_metadata_passthrough`를 제거하도록 수정됐습니다. 도구 인자·출력·호출 ID·메시지 내용은 보존하며, 모델·런타임 설정이나 다른 공급자 경로는 변경하지 않았습니다. 재사용 가능한 [최소 어댑터 및 자체 테스트](../scripts/ninfer-codex-input-compat.py)를 제공하지만 완전한 라우터는 아닙니다.

수정 후 같은 프롬프트·원래 픽스처·Codex CLI로 1회 재검증했습니다. Codex는 소스와 테스트를 읽고, 합계 함수를 수정하고, 테스트를 실행한 뒤 최종 응답을 반환했습니다. 독립적인 `node sum.test.cjs` 실행도 검증 3개를 모두 통과했습니다. 보존된 읽기 출력과 최종 테스트 파일은 일치했고 소스 함수만 변경됐습니다. 메타데이터 HTTP 400 오류는 재발하지 않았습니다.

| 지표 | 수정 후 관측값 |
| --- | ---: |
| Codex 종료 코드 / 실제 경과 시간 | 0 / 33.409 s |
| 성공한 도구 실행 | 2 (읽기; 수정 + 테스트) |
| API 생성 횟수 | 3 |
| 요청별 실제 프롬프트 토큰 | 94,338 / 94,544 / 94,682 |
| 총 입력 / 캐시된 입력 / 출력 토큰 | 283,564 / 188,770 / 247 |
| 추론 출력 토큰 | 0 |
| 요청별 서버 디코딩 tok/s | 183.2 / 174.5 / 140.5 |
| 요청별 클라이언트 측에 보고된 서버 TTFT | 19.2 s / 197 ms / 313 ms |
| 수락 / 제안 토큰 | 169 / 249 (67.87%) |
| 독립 픽스처 테스트 | 3/3 PASS |

출력 길이가 각각 48/79/120토큰에 불과하므로 대표적인 에이전트 TPS 벤치마크나 전체 CourseBench 성공의 근거가 아닙니다. 최초 집계 대상 실패를 대체하지 않는, 명시적인 수정 후 재검증입니다. 하니스 콘솔 출력은 Codex의 성공 종료와 UTF-8 로그를 저장한 **뒤에** Windows 인코딩 오류를 겪었습니다. 저장된 결과와 독립 테스트로 성공 여부를 확인했습니다. 비치명적인 WebSocket→HTTP 폴백과 로컬 hook/MCP 종료 경고도 남았으며, 런타임 정확성 실패가 아니고 이번 범위에서 수정하지 않았습니다.

결과: **어댑터 수정 후 제한된 Codex 도구 왕복 호환성 PASS. 장기 자율 작업용 승격은 아직 검증되지 않았습니다.**

## 공개 범위

이번 실행에서는 GPUQ 취소가 자동 완료됐습니다. 예약이 취소 상태가 되고 포트 8083이 닫혔으며, 관측된 장치 전체 메모리가 83 MiB로 돌아왔습니다. 이는 9월 8일 통합 보고서에서 미검증이었던 정리 경로를 확인한 결과입니다.

이 보고서는 실패 결과와 기존 Q5 측정값을 보존합니다. 공개 라우팅은 Q5를 기본값, NInfer를 명시적으로 선택할 수 있는 후보, SGLang을 서빙 경로로 유지합니다. 모델 가중치, 비공개 소스, 세션 식별자, 장비의 원본 로그는 공개하지 않습니다.
